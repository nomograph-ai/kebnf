# Formal Semantics: KEBNF → tree-sitter Transformation

**Status**: Skeleton (for MODELS/SLE 2026 paper)  
**Last Updated**: 2026-02-13  
**Target Venue**: MODELS 2026 or SLE 2026

## Overview

This document formalizes the transformation from OMG KEBNF (KerML Extended BNF) specifications to tree-sitter grammars. The formalization serves two purposes:

1. **Scientific rigor** for MODELS/SLE publication
2. **Correctness arguments** for the transformation tool

## Motivation

OMG publishes language specifications using KEBNF, a variant of EBNF with metamodel annotations. Official tooling from these specifications takes 18-24 months. tree-sitter enables immediate syntax highlighting, navigation, and analysis.

**Research question**: Can we formally characterize the KEBNF→tree-sitter transformation to understand its semantic properties (soundness, completeness, ambiguity)?

## Notation

We use standard notation for formal language definitions:

- $\mathcal{L}(G)$ - Language generated by grammar $G$
- $\Rightarrow^*$ - Derives in zero or more steps
- $|$ - Alternation
- $[\cdot]$ - Optional
- $\{\cdot\}$ - Zero or more repetitions
- $(\cdot)$ - Grouping

## Part 1: KEBNF Abstract Syntax

### 1.1 Grammar Definition

A KEBNF grammar $K$ is a tuple $(N, T, P, S, M)$ where:

- $N$ is a finite set of non-terminal symbols
- $T$ is a finite set of terminal symbols
- $P$ is a finite set of production rules
- $S \in N$ is the start symbol
- $M : N \rightarrow \text{Metaclass}$ maps non-terminals to metamodel classes

### 1.2 Production Rules

A KEBNF production rule has the form:

$$
A ::= \alpha \quad [\text{metamodel-annotation}]
$$

where $A \in N$ and $\alpha$ is a sequence of:

- Terminals: `'keyword'` or `"keyword"`
- Non-terminals: `RuleName`
- Optional: `[ \alpha ]`
- Repetition: `{ \alpha }` (zero or more) or `{ \alpha }+` (one or more)
- Alternation: `\alpha_1 | \alpha_2`
- Grouping: `( \alpha )`

### 1.3 Metamodel Annotations

KEBNF extends EBNF with metamodel annotations:

```
PartDefinition ::= ... ;      # Creates PartDefinition metaclass instance
ownedRelationship += ...      # Adds to ownedRelationship collection
```

**For tree-sitter transformation**: Metamodel annotations are preserved as comments/metadata but do not affect parsing behavior.

### 1.4 Formal Definition of KEBNF Expressions

$$
\begin{aligned}
\text{Expr} ::= & \quad t & \text{(terminal } t \in T \text{)} \\
              | & \quad A & \text{(non-terminal } A \in N \text{)} \\
              | & \quad \text{Expr}_1 \text{Expr}_2 & \text{(sequence)} \\
              | & \quad \text{Expr}_1 | \text{Expr}_2 & \text{(alternation)} \\
              | & \quad [ \text{Expr} ] & \text{(optional)} \\
              | & \quad \{ \text{Expr} \} & \text{(zero-or-more)} \\
              | & \quad \{ \text{Expr} \}^+ & \text{(one-or-more)} \\
              | & \quad ( \text{Expr} ) & \text{(grouping)}
\end{aligned}
$$

## Part 2: tree-sitter Grammar Abstract Syntax

### 2.1 Grammar Definition

A tree-sitter grammar $G$ is a JavaScript object defining:

```javascript
{
  name: string,
  rules: { [name: string]: Rule },
  extras: Rule[],
  conflicts: string[][],
  precedences: [string[]][]
}
```

### 2.2 Rule Constructors

tree-sitter provides these rule constructors:

| Constructor | Meaning |
|-------------|---------|
| `$.rule_name` | Reference to rule |
| `'literal'` | String literal |
| `/regex/` | Regular expression |
| `seq(r1, r2, ...)` | Sequence |
| `choice(r1, r2, ...)` | Alternation |
| `optional(r)` | Zero or one |
| `repeat(r)` | Zero or more |
| `repeat1(r)` | One or more |
| `prec(n, r)` | Precedence |
| `prec.left(n, r)` | Left associative |
| `prec.right(n, r)` | Right associative |
| `field(name, r)` | Named field |
| `alias(r, name)` | Rename in AST |
| `token(r)` | Treat as single token |

### 2.3 Formal Definition of tree-sitter Rules

$$
\begin{aligned}
\text{Rule} ::= & \quad \text{ref}(n) & \text{(rule reference)} \\
              | & \quad \text{lit}(s) & \text{(literal string)} \\
              | & \quad \text{regex}(r) & \text{(regular expression)} \\
              | & \quad \text{seq}(\text{Rule}^*) & \text{(sequence)} \\
              | & \quad \text{choice}(\text{Rule}^*) & \text{(alternation)} \\
              | & \quad \text{optional}(\text{Rule}) & \text{(optional)} \\
              | & \quad \text{repeat}(\text{Rule}) & \text{(zero-or-more)} \\
              | & \quad \text{repeat1}(\text{Rule}) & \text{(one-or-more)} \\
              | & \quad \text{prec}(n, \text{Rule}) & \text{(precedence)}
\end{aligned}
$$

## Part 3: Transformation Function

### 3.1 Core Transformation

Define transformation $\mathcal{T} : \text{KEBNF} \rightarrow \text{tree-sitter}$

$$
\mathcal{T}[\![ K ]\!] = G \text{ where } G.\text{rules} = \{ n \mapsto \mathcal{T}_r[\![ p ]\!] \mid (n ::= p) \in K.P \}
$$

### 3.2 Expression Transformation

$$
\begin{aligned}
\mathcal{T}_r[\![ t ]\!] &= \text{lit}(t) \\
\mathcal{T}_r[\![ A ]\!] &= \text{ref}(A) \\
\mathcal{T}_r[\![ e_1 e_2 ]\!] &= \text{seq}(\mathcal{T}_r[\![ e_1 ]\!], \mathcal{T}_r[\![ e_2 ]\!]) \\
\mathcal{T}_r[\![ e_1 | e_2 ]\!] &= \text{choice}(\mathcal{T}_r[\![ e_1 ]\!], \mathcal{T}_r[\![ e_2 ]\!]) \\
\mathcal{T}_r[\![ [ e ] ]\!] &= \text{optional}(\mathcal{T}_r[\![ e ]\!]) \\
\mathcal{T}_r[\![ \{ e \} ]\!] &= \text{repeat}(\mathcal{T}_r[\![ e ]\!]) \\
\mathcal{T}_r[\![ \{ e \}^+ ]\!] &= \text{repeat1}(\mathcal{T}_r[\![ e ]\!]) \\
\mathcal{T}_r[\![ ( e ) ]\!] &= \mathcal{T}_r[\![ e ]\!]
\end{aligned}
$$

### 3.3 Conflict Resolution

KEBNF grammars often have LR conflicts that tree-sitter cannot resolve automatically. We introduce:

$$
\mathcal{T}_c : \text{KEBNF} \times \text{Conflicts} \rightarrow \text{tree-sitter}
$$

where $\text{Conflicts}$ is a set of resolution strategies:

- **Precedence**: Add `prec(n, r)` to prefer one alternative
- **Inline**: Replace rule reference with rule body
- **Refactor**: Split rule into multiple rules
- **External**: Mark as external scanner

## Part 4: Semantic Properties

### 4.1 Soundness (Over-approximation)

**Theorem (Soundness)**: For KEBNF grammar $K$ and its transformation $G = \mathcal{T}[\![ K ]\!]$:

$$
\mathcal{L}(K) \subseteq \mathcal{L}(G)
$$

*Informal*: tree-sitter grammar accepts at least everything KEBNF accepts.

**Proof sketch**: Each KEBNF construct maps to equivalent or more permissive tree-sitter construct. The transformation does not add restrictions.

### 4.2 Completeness (Under-approximation)

**Conjecture**: There exist KEBNF grammars $K$ where:

$$
\mathcal{L}(G) \supsetneq \mathcal{L}(K)
$$

*Informal*: tree-sitter grammar may accept programs that KEBNF rejects.

**Known sources of over-acceptance**:
1. Lookahead limitations (tree-sitter has finite lookahead)
2. Context-sensitive features (e.g., whitespace sensitivity)
3. Metamodel constraints (not expressible in CFG)

### 4.3 Ambiguity Preservation

**Observation**: KEBNF grammars may be intentionally ambiguous (metamodel resolves ambiguity). tree-sitter requires disambiguation.

Our transformation introduces disambiguation via:
- Precedence declarations
- Conflict tables
- Rule refactoring

**Open question**: How to characterize the disambiguation choices and their impact on accepted language?

## Part 6: Pattern Catalog

Document recurring transformation patterns:

### Pattern 1: Simple Alternation

**KEBNF**:
```
TypeBody ::= ';' | '{' TypeBodyItem* '}' ;
```

**tree-sitter**:
```javascript
type_body: $ => choice(
  ';',
  seq('{', repeat($.type_body_item), '}')
)
```

### Pattern 2: Left-Recursive List

**KEBNF**:
```
QualifiedName ::= Identifier ( '::' Identifier )* ;
```

**tree-sitter**:
```javascript
qualified_name: $ => seq(
  $.identifier,
  repeat(seq('::', $.identifier))
)
```

### Pattern 3: Operator Precedence

**KEBNF** (ambiguous):
```
Expression ::= Expression '+' Expression | Expression '*' Expression | ... ;
```

**tree-sitter** (disambiguated):
```javascript
expression: $ => choice(
  prec.left(1, seq($.expression, '+', $.expression)),
  prec.left(2, seq($.expression, '*', $.expression)),
  // ...
)
```

## Part 7: Limitations and Future Work

### Known Limitations

1. **Metamodel constraints**: Cannot enforce semantic constraints in CFG
2. **Whitespace sensitivity**: Some KEBNF features require lexer modes
3. **Ambiguity resolution**: Manual intervention required for LR conflicts
4. **Error recovery**: tree-sitter error recovery may differ from intended

### Future Work

1. **Automated conflict resolution**: ML-based suggestion of precedence values
2. **Partial correctness proofs**: Mechanize soundness proof in Coq/Lean
3. **Metamodel integration**: Generate semantic checks alongside parser
4. **Bidirectional transformation**: Generate KEBNF from tree-sitter (for validation)
